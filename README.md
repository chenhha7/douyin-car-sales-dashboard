# 抖音本地生活卖车经营看板（Demo）

用于数据分析作品集展示的静态互动看板。项目以**完全合成**的用户级事件，模拟抖音本地生活卖车场景中，从抖音内容触达、团购券购买或留资，到理想内部销售承接、到店 / 试驾及最终锁单的经营分析。

> 数据隐私声明：仓库中的用户、服务商、直播间、门店、订单、金额、时间和转化指标均由脚本生成，均为虚构示例；不包含真实业务数据、渠道编码、生产系统信息、凭据或个人信息。

## 看板回答的业务问题

1. 抖音带来的订单、留资与内部销售链路能否关联，最终是否带来真实锁单？
2. 用户主要流失在哪一环：创建商机、开启商机、门店承接、预约到店、试驾还是锁单？
3. 直播间、私信、服务商和门店之间的规模与效率差异，如何支持资源倾斜和结算复盘？
4. 抖音带来的锁单主要是新增用户、激活历史未成交用户，还是促进原有销售跟进用户决策？
5. 当订单、退款、承接或锁单效率发生异常时，如何定位到服务商、内容资产、直播间、区域、门店或产品系列？
6. 当门店承接 SOP 上线后，区域的创建→开启时效与成熟锁单表现是否改善，哪些区域具备扩围条件？

## 业务链路与关联原则

```text
抖音可识别转化入口（直播间 / 私信）
        ↓
团购券购买 或 留资
        ↓
关联理想内部线索与商机
        ↓
毛线索 → 净线索 → 创建商机 → 开启商机 → 门店下发承接 → 预约到店 → 到店 / 试驾 → 锁单
```

订单、留资和内部线索 / 商机并不是三批互斥用户，也不被强行写成“订单 → 线索”的单一路径。看板以用户级关联键串联可识别的抖音入口、订单、线索和销售节点：团购券用户通常具备较高意向，私信留资需经过销售判断；同时，用户在抖音入口发生前也可能已有内部销售跟进。

## 三页看板结构

| 页面 | 主要内容 | 支持的决策 |
| --- | --- | --- |
| 经营看板 | 订单、毛 / 净线索、创建 / 开启商机、门店承接、到店 / 试驾、锁单；团购券履约；区域 SOP 上线前后同期用户组对比；直播间与服务商拆解；用户明细 | 识别瓶颈、调整承接策略、评估投放与服务商效果 |
| 渠道价值分析 | 对锁单用户按抖音触达前 CRM 状态分为新增贡献、战败激活、存量促转 | 判断渠道的关联贡献和重点价值，不将关联直接表述为因果增量 |
| 异常归因与经营诊断 | 指标拆解树、因子贡献、多维贡献拆分与用户明细下钻；按服务商、来源 / 内容、直播间、区域、门店、产品系列定位 | 解释订单、开启商机、门店承接、到店 / 试驾、锁单或退款的变动来自规模还是某一环节效率 |

异常归因页不使用抖音曝光、观看人数或点击数据：这些平台前链路数据在该业务协作模式下不可得。订单、毛线索、退款等入口指标按来源 / 服务商 / 直播间的实际可识别数量进行加法拆分；内部销售指标再按“规模 × 环节效率”拆解，并展示最近 7 个触达日的具体数据作为佐证。

## 核心口径

### 经营与销售转化

- 商品订单数：成功购买团购券的订单数；同步监控待使用、已核销与已退款。
- 毛线索 / 净线索：抖音触达后可关联到内部销售体系的线索，以及经业务规则筛选后的净线索。
- 创建商机 / 开启商机：由销售判断意向后创建，及后续完成开启的商机；`创开率 = 开启商机 / 创建商机`。
- 门店承接：已开启商机被下发并由门店接收；`门店承接率 = 门店已承接 / 开启商机`。
- 锁单：已完成最终锁单的商机。

“创建商机 → 开启商机”是 Demo 重点观察的销售流失环节。分析时应先检查门店分单、跟进覆盖和待开启商机，再决定是否扩大流量。

### 成熟商机

锁单需要观察期，近期创建的商机不能直接与较早批次比较。因此锁单率、7 日锁单率和创建→锁单周期默认使用已进入 14 天观察窗口的**成熟商机群**，避免新商机尚未转化造成假性下降。

### 区域 SOP 上线前后同期用户组对比

看板在整体漏斗之后增加“区域承接优化 · 门店 SOP 宣贯效果”模块，形成“发现创建→开启损失 → 区域定位 → SOP 上线 → 验证效果 → 决定扩围”的经营闭环。

- Demo 宣贯上线日：`2026-07-14`（合成场景）。
- 上线前 / 后同期用户组：分别取 `2026-06-16` 至 `2026-07-13`、`2026-07-14` 至 `2026-08-10` 创建销售记录的用户；两个窗口均为 28 天。
- 观察截止：`2026-09-09`。因此上线后最后一批用户也具备完整 30 天观察期。
- 3 日创开率：`创建销售记录后 72 小时内完成开启 / 创建销售记录数`，衡量门店是否及时完成商机开启。
- 30 日内锁单率：`创建后 30 天内锁单 / 已具备 30 天观察期的创建销售记录数`，衡量商机开启改善是否继续传导至最终结果。

该模块用于展示同期用户组评估方法，不将 Demo 的前后差异直接写成真实项目的因果结论。真实复盘应接入实际宣贯日期、门店覆盖清单和用户级销售节点；若门店分批上线，可进一步采用同期未上线门店作为对照组评估增量。

### 渠道价值分层

仅对最终锁单且关联抖音触达的用户，按触达前 CRM 状态赋予一个互斥标签：

| 触达前状态 | 价值标签 | 含义 |
| --- | --- | --- |
| 无有效历史记录 | 新增贡献 | 抖音触达后首次进入可追踪销售流程并锁单 |
| 历史战败或长期未成交 | 战败激活 | 抖音内容或权益带动历史停滞用户重新推进 |
| 已有进行中商机或销售跟进 | 存量促转 | 用户原本已在销售流程中，抖音触达与其后续锁单相关联 |

这不是首次触达归因或末次触达归因，也不直接宣称严格因果增量；它用于展示渠道关联的业务价值结构。

## 本地运行

项目不依赖第三方 Python 包，使用 Python 3.10+ 即可：

```bash
python scripts/run_demo.py
python -m http.server 8000
```

访问 `http://localhost:8000` 即可查看看板。

`scripts/run_demo.py` 会依次执行：

```text
生成合成用户事件 → 加工用户级漏斗、时效与成熟队列 → 聚合多维指标 → 校验数据质量与公开发布边界
```

## 数据文件

```text
data/demo/raw_funnel_records.json   # 合成的原始用户触达、订单、线索和销售事件
data/demo/attribution_detail.json   # 看板使用的用户级明细、时效、触达前 CRM 状态与价值标签
data/demo/attribution_summary.json  # 全局、日度与多维聚合统计
data/demo/data_quality_report.json  # 数据质量与公开发布边界校验
```

完整口径见 [docs/attribution-rules.md](docs/attribution-rules.md)。
